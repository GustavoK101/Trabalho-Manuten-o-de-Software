Ponto de Partida

O projeto original

O ponto de partida é o exemplo oficial do tutorial do Socket.IO — um chat minimalista criado para ensinar os conceitos básicos de comunicação em tempo real. O código era funcional para fins didáticos, mas não estava preparado para uso real: sem validação, sem testes, sem modularização e com bugs que passariam despercebidos em produção.

  • 📁 Apenas 2 arquivos: index.js e index.html Todo o servidor — cluster, banco, rotas e socket — estava em um único arquivo de 84 linhas.
  • 🗄️ Persistência com SQLite Mensagens salvas localmente com offset único por cliente para garantir entrega idempotente.
  • ⚙️ Node.js Cluster + @socket.io/cluster-adapter Um worker por CPU, com o adaptador de cluster sincronizando eventos entre processos.
  • 🔄 Connection State Recovery Ao reconectar, o cliente envia o último ID recebido e o servidor reenvia apenas o que faltou.
Análise do Código

Problemas identificados

Uma leitura cuidadosa do código revelou quatro problemas que, em um ambiente de produção, causariam falhas silenciosas ou comportamento imprevisível.

Bug

Verificação de erro por número mágico

e.errno === 19 é o número interno do SQLite para constraint violation. Esse valor não é parte da API pública e pode mudar entre versões da biblioteca, tornando a verificação frágil e ilegível.

Bug

Erros de banco completamente silenciados

Dois blocos catch com comentário "nothing to do" e "something went wrong" descartavam qualquer exceção sem log, tornando impossível diagnosticar falhas em produção.

Bug

Porta sem valor padrão

O servidor usava process.env.PORT diretamente. Se a variável não fosse definida, server.listen(undefined) escolhia uma porta aleatória sem nenhum aviso — comportamento difícil de depurar.

Vulnerabilidade

Ausência total de validação de entrada

Qualquer dado enviado pelo cliente era inserido diretamente no banco: payloads não-string, mensagens vazias ou textos de megabytes seriam aceitos sem restrição, abrindo brechas para crash ou abuso.

Correções

Como cada bug foi resolvido

Antes
// número mágico sem semântica
if (e.errno === 19) {
  callback();
} else {
  // nothing to do
}

// erros ignorados
} catch (e) {
  // something went wrong
}

// porta sem fallback
const port = process.env.PORT;
Depois
// código de erro estável da API
if (e.code === 'SQLITE_CONSTRAINT') {
  callback();
} else {
  console.error('DB insert error:', e);
}

// erros sempre logados
} catch (e) {
  console.error('Recovery error:', e);
}

// fallback seguro
const port = process.env.PORT || 3000;

A validação de entrada foi adicionada como primeira instrução do handler: rejeita qualquer mensagem que não seja string, esteja vazia (apenas espaços) ou ultrapasse 500 caracteres — respondendo ao cliente com { error: 'invalid message' } antes de qualquer acesso ao banco.

Refatoração

Separação de responsabilidades

O index.js original misturava cluster, banco de dados, configuração de servidor e lógica de negócio em um único arquivo. Aplicamos o Princípio da Responsabilidade Única (SRP) dividindo o código em três módulos coesos:

db.js

Camada de dados

Responsável exclusivamente por abrir a conexão com o SQLite e garantir que o schema existe. Usa process.env.DB_FILE, o que permite trocar para :memory: nos testes sem alterar nenhum outro arquivo.

chat.js

Lógica de negócio

Registra todos os eventos do Socket.IO: recebimento e broadcast de mensagens, indicador de digitação, recuperação de histórico. Recebe io, socket e db por injeção — completamente testável de forma isolada.

index.js

Camada de montagem

Gerencia cluster, instancia Express, cria o servidor HTTP, configura Socket.IO com o cluster adapter e monta os handlers. Não contém lógica de chat — apenas conecta as peças.

Resultado: cada arquivo pode ser lido, entendido e modificado de forma independente. Os testes importam apenas db.js e chat.js, sem precisar subir o cluster.

Novas Funcionalidades

O que foi adicionado

Feature

👤 Nomes de usuário

Ao abrir o chat, o usuário escolhe um nome (máx. 30 caracteres). O nome é enviado via socket.handshake.auth, persistido na coluna username do banco e exibido ao lado de cada mensagem.

Feature

⌨️ Indicador de digitação

Enquanto digita, o cliente emite typing ao servidor, que reencaminha aos outros via socket.broadcast. Após 2 segundos sem digitar, stop typing é enviado automaticamente e o indicador desaparece.

Feature

🕐 Timestamp nas mensagens

O banco armazena created_at em UTC usando strftime do próprio SQLite. O servidor inclui o valor no evento emitido; o cliente converte para horário local usando toLocaleTimeString('pt-BR').

Feature

🔔 Mensagens do sistema

Quando um usuário conecta ou desconecta, o servidor emite system message para todos os clientes. Exibidas de forma diferenciada — centralizadas, em itálico, cor cinza — para não poluir o fluxo de mensagens.

Feature

👥 Usuários online

O servidor mantém um Map de socketId → username. A cada conexão ou desconexão, a lista atualizada é enviada a todos via online users. A sidebar mostra o ponto verde ao lado de cada nome.

Feature

✉️ Mensagens privadas (1-a-1)

Clicando em um nome na sidebar, abre-se um painel flutuante de chat privado. O evento private message usa socket.to(targetId) para entregar apenas ao destinatário — terceiros não recebem o evento.

Experiência do Usuário

Melhorias de interface

Além das funcionalidades de negócio, a interface foi completamente reescrita para ser mais usável e informativa, seguindo padrões de chat modernos.

  • 📊 Contador de caracteres em tempo real Mostra o total restante (500 − digitado). Fica amarelo abaixo de 100, vermelho ao ultrapassar o limite — feedback visual imediato sem bloquear a digitação.
  • ↩️ Enter envia · Shift+Enter insere nova linha Comportamento padrão de chats modernos (Slack, WhatsApp Web). O campo crescia como textarea e o submit era interceptado via keydown.
  • 📐 Textarea auto-redimensionável O campo cresce junto com o texto até 8 linhas, depois rola internamente — sem empurrar o layout da página.
  • 🗂️ Sidebar de usuários online Lista lateral fixa com indicador verde por usuário. Clique em qualquer nome abre diretamente o painel de mensagem privada.
  • 💬 Painel de chat privado flutuante Posicionado no canto inferior direito, abre automaticamente ao receber uma mensagem privada de outro usuário, sem interromper o chat principal.
Qualidade de Software

Testes automatizados

O projeto não tinha nenhum teste. Criamos uma suite de integração usando Vitest e socket.io-client, com um servidor real e banco SQLite :memory: instanciado antes dos testes e descartado ao fim — sem mocks frágeis, testando o fluxo completo.

6 testes · Mensagens

Fluxo principal de chat

Broadcast para todos os clientes · timestamp incluído no evento · rejeição de mensagem vazia · rejeição acima de 500 chars · rejeição de payload não-string · idempotência por client_offset (segundo envio com mesmo offset não gera novo broadcast).

2 testes · Digitação

Indicador de digitação

Evento typing chega ao cliente correto com o nome do usuário · evento stop typing também é reencaminhado com o nome correto. Verifica que o socket.broadcast não devolve ao próprio emissor.

2 testes · Sistema

Mensagens de sistema

Ao conectar, todos recebem "X entrou no chat" com o nome correto · ao desconectar, todos recebem "X saiu do chat". Testa o ciclo completo de conexão e desconexão.

2 testes · Privadas

Mensagens 1-a-1

Mensagem privada chega apenas ao destinatário correto — um terceiro cliente conectado não recebe o evento · mensagem com conteúdo vazio é descartada silenciosamente no servidor sem emitir nada.

✅ 12 testes, todos passando · tempo médio de execução: ~480ms

Tecnologia

Stack e decisões técnicas

⚡ Socket.IO 4

Biblioteca de comunicação bidirecional sobre WebSocket com fallback para long-polling. Oferece reconexão automática, acknowledgements, rooms e namespaces nativamente. Usamos o cluster adapter para sincronizar eventos entre workers do Node.js.

🟢 Node.js + Express

Express serve o HTML estático na rota GET /. O cluster nativo do Node.js cria um worker por CPU lógica, maximizando throughput sem dependências externas — o processo primário apenas distribui conexões e sincroniza o Socket.IO.

🗄️ SQLite (via pacote sqlite)

Banco embarcado, sem servidor separado. A tabela messages armazena content, username, client_offset (chave única para idempotência) e created_at gerado automaticamente pelo banco em UTC.

🧪 Vitest + socket.io-client

Runner de testes com suporte nativo a ESM, sem necessidade de transpilação. O socket.io-client conecta a um servidor real instanciado na porta 0 (aleatória) durante os testes, garantindo isolamento e sem conflito de portas.

Próximos Passos

O que ainda pode ser feito

O projeto está funcional e testado, mas ainda há espaço para evoluir em direção a um produto completo. As melhorias abaixo são ordenadas por impacto e viabilidade.

Alta prioridade

🏠 Salas e canais

Criar ou entrar em salas nomeadas usando socket.join(room). Mensagens ficam restritas à sala — base para separar grupos de conversa, como canais de um Slack.

Alta prioridade

🚦 Rate limiting

Limitar a quantidade de mensagens por cliente por segundo no servidor. Evita flood e abuso, protegendo o banco e os outros clientes de spam automatizado.

Média prioridade

🔐 Autenticação com JWT

Substituir o nome livre por um login com token. O middleware do Socket.IO valida o JWT antes de aceitar a conexão — nomes autenticados, sessões persistentes entre abas.

Média prioridade

🔍 Busca no histórico

Endpoint REST ou evento Socket.IO que busca mensagens no banco por palavra-chave usando LIKE no SQLite. Retorna com paginação para não sobrecarregar.

Baixa prioridade

😄 Reações a mensagens

Clique em uma mensagem para adicionar uma reação de emoji. Contadores por reação, persistidos no banco em uma tabela de relação reactions(message_id, emoji, user).

Baixa prioridade

📁 Envio de arquivos

Upload de imagens e arquivos via Socket.IO ou um endpoint multipart do Express. Armazenar no disco ou em object storage (S3), exibir pré-visualização inline no chat.
